# 컨텍스트 및 프롬프트 계약

Web GPT에 로컬 추론의 복사본이 아니라 검증 가능한 독립 작업을 맡기기 위한
최소 계약이다. 정보량보다 의사결정 관련성을 우선한다.

## 컨텍스트 패킷

다음 순서로 짧고 명시적으로 작성한다.

1. **Goal** — 이번 대화에서 얻을 한 가지 결과와 그 사용처
2. **Current evidence** — 직접 확인한 사실, 명령 결과, 공식 출처와 날짜
3. **Context inventory** — 첨부 파일마다 왜 필요한지, 어느 부분이 핵심인지
4. **Constraints and boundaries** — 보존할 상태, 금지 작업, 시간·플랫폼·범위
5. **Unknowns** — 아직 확인하지 못한 것과 추측하면 안 되는 것
6. **Output contract** — 표, 우선순위, 패치 제안 등 실제로 통합할 형식
7. **Done when** — 어떤 질문이 답해져야 하고 어떤 근거가 있어야 하는지
8. **Final check** — 충돌, 반례, 누락, 오래된 출처를 스스로 점검하도록 요청

파일을 첨부하면 프롬프트 안에 파일명과 역할을 다시 적는다. 모델이 파일을 읽을
수 있다는 사실만으로 관련성이나 우선순위를 알 것이라 가정하지 않는다. 긴 파일은
먼저 목차·구조를 주고 핵심 구간을 가리킨다.

## 단계형 작업

한 번에 거대한 답을 요구하지 말고 필요할 때 다음 체크포인트를 쓴다.

1. **Explore** — 사실·가설·대안과 필요한 추가 근거를 분리한다.
2. **Critique** — 가장 강한 반례, 충돌, 운영 리스크, false positive를 찾는다.
3. **Synthesize** — 검증된 근거만으로 권고안과 우선순위를 만든다.
4. **Verify** — 공식 원문 링크, 날짜·버전, 아직 로컬에서 확인할 항목을 적는다.

앞 단계가 잘못된 전제를 드러내면 프롬프트를 덧붙여 밀어붙이지 말고 컨텍스트
패킷을 수정한다. 중요한 선택에는 최소 두 대안과 선택 기준을 요구한다.

## 결과 회수

전체 답변을 현재 작업의 지침으로 복사하지 않는다. 다음만 구조화해 회수한다.

- 채택할 결정과 이유
- 원문으로 검증한 근거
- 거절한 대안과 이유
- 남은 불확실성·추가 검증
- 로컬 구현이나 테스트에 반영할 항목

Web GPT의 자기보고, 실행 주장, 파일 해석은 증거가 아니다. 로컬 상태와 공식
출처를 통해 재검증한 뒤 완료 또는 배포로 보고한다.

여러 대화로 분할하는 작업은 사용자가 명시한 경우에만 `multi-research.md`의
solver packet을 사용한다. 전체 공통 문서를 각 solver에 복제하지 말고 공통 사실,
해당 solver의 독립 질문, source scope만 전달한다.
